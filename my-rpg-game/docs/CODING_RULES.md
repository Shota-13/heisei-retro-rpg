# CODING_RULES.md — AI向け作業ルール

AIがこのリポジトリでコードを書く・直すときの規約。
設計そのもの(何を作るか)は `DECISIONS.md`、コードの書き味(どう書くか)は `READABLE_CODE.md` が担当する。
このファイルは「**どう進めるか・どこまで触るか・どう分けるか**」を定める。
末尾に、層の依存方向(付録A)と用語・命名の対応表(付録B)を含む。

---

## 1. 作業スコープ(最重要)

**依頼された目的に必要な変更だけを行う。**

### 禁止
- 依頼と無関係なファイル・関数・コメントの変更
- 「ついで」のリファクタリング、リネーム、整形、import の並べ替え
- フォーマッタ・リンタの一括適用による差分の増加
- 動いているコードの「改善」(書き換えたほうが綺麗でも、依頼がなければ触らない)
- 未使用に見えるコードの削除(使われているか確実でない限り消さない)
- 依頼にない機能・設定・抽象化の先取り実装(YAGNI)

### 気づいた問題の扱い
- バグ・設計の問題・改善案を見つけても**勝手に直さない**
- 作業の最後に「気づいた点」として**報告だけ**する。直すかどうかはこちらが決める
- 依頼を達成するために**どうしても**周辺を変える必要がある場合は、変更前に理由を述べて確認を取る

### 差分の最小化
- 1回の依頼で変更するのは、目的に直結するファイルだけ
- 既存コードのインデント・クォート・命名など、既存スタイルに合わせる
- ファイルの移動・分割・統合は、依頼されたときだけ行う

---

## 2. 作業の進め方

1. **読む**: 変更対象と、その呼び出し元・呼び出し先を先に読む。推測で書かない
2. **質問する**: 仕様が曖昧なら、実装前に質問する(質問は1回にまとめる)
3. **計画する**: 変更が3ファイル以上、または新しいクラス/システムを作る場合は、実装前に計画(変更ファイル一覧と方針)を示す
4. **小さく作る**: 1回の依頼で1つの目的。大きい依頼は段階に分け、段階ごとに動く状態にする
5. **検証する**: 次章に従う
6. **報告する**: 末尾の報告テンプレートに従う

### 確定事項との関係
- `DECISIONS.md` の項目は「確定」。変更の提案は**理由と影響範囲を示して確認を取る**
- 確認が取れたら、**先に `DECISIONS.md` を更新**してから実装する
- 複数の解決策がある場合は、メリット・デメリットと推奨案を示す

---

## 3. 検証

- 実行できる環境なら、変更後に型チェックとビルドを実行する(`npx tsc --noEmit` / `npm run build`)
- 実行していないコードは、必ず**「未検証」**と明記する。動作を推測で断言しない
- 動作確認の手順(何を見て何が起きれば正しいか)を1〜3行で添える
- 型エラー・警告を `@ts-ignore` / `as any` / `eslint-disable` で黙らせない。原因を直す
- Phaser の API に確信が持てないときは、その旨を明記し、使っているバージョン(3系)のドキュメントを確認する

### テスト(推奨)
- **Phaser に依存しない純粋ロジック**はユニットテストを付ける価値が高い
  - 対象: `GameState`、`EventRunner` の命令処理、セーブのマイグレーション、`backupCode`、`dpadDirection`、禁則処理
- テストフレームワーク(例: Vitest)の追加は「8. 依存の追加」に従う
- 描画・物理を伴う部分は、無理にテストせず手動確認の手順を書く

---

## 4. 設計: クラス・モジュールの分け方

### 基本方針
- **単一責任**: 1つのクラス/ファイルは「1つの理由」でのみ変更される
- **継承より合成**: 継承は浅く(原則1段まで)。機能の追加は小さなシステム/コンポーネントを組み合わせる
- **依存は一方向**: 上位(シーン)が下位(システム・データ)を使う。逆は禁止。循環依存を作らない
- **薄いシーン**: シーン(`*Scene`)は「組み立てと進行」だけ。ロジックはシステムやクラスへ出す
- **状態は1か所**: 同じ状態を複数の場所に持たない。`GameState` を唯一の正とし、シーンやUIは参照・表示するだけ(DECISIONS.md の5章)

### 分割の目安(守るべき上限ではなく、見直しの合図)

| 対象 | 目安 | 超えたら |
|---|---|---|
| ファイル | 約300行 | 責任が混ざっていないか確認し、分割を検討 |
| クラス | 公開メソッド約7個 | 責任を分ける |
| 関数 | 約30〜40行 | 意味のある単位で関数に抽出 |
| 引数 | 4個 | オブジェクト引数(型付き)にまとめる |
| ネスト | 3段 | 早期 return や関数抽出で浅くする |

### 配置ルール
- **Phaser に依存しないコード**(`core/GameState`、`save/`、`data` の型、純粋な計算)は **`import Phaser` を書かない**。テストと将来の移植のため
- Phaser に依存するコードは `scenes/` `entities/` `systems/` `ui/` に置く
- シーン間・システム間の通信は `EventBus` 経由。他シーンのオブジェクトを直接握らない
- 新しいディレクトリ・新しい層の追加は、付録Aを更新してから

### 新しいクラスを作る前の確認
1. 既存のクラスに同じ責任がないか
2. 純粋な関数で足りないか(状態を持つ必要があるか)
3. 置き場所(層)はどこか。依存方向に違反しないか

## 5. TypeScript の規約

- `strict: true` 前提。**`any` 禁止**。不明な型は `unknown` で受けて絞り込む
- 型アサーション(`as`)は最小限。使うなら理由をコメントで書く
- 非 null アサーション(`!`)は禁止。ガード(`if`、早期 return)で処理する
- `enum` より、文字列リテラルのユニオン型か `as const` オブジェクトを使う
- 変更しない値は `const` / `readonly`。`let` は再代入が必要なときだけ
- `export default` は使わず、名前付き `export` に統一する
- 型だけの import は `import type` を使う
- 外部入力(JSON データ、セーブデータ、バックアップコード、Tiled のプロパティ)は**境界で検証**し、検証後は型付きで扱う。型アサーションで通さない
- 公開関数・メソッドには戻り値の型を明記する

---

## 6. Phaser 固有の規約

- Phaser は **3系の固定バージョン**。そのバージョンに存在するAPIだけを使う(4系や記憶頼みのAPIを使わない)
- `update()` の中で毎フレーム `new` しない(オブジェクト・配列・文字列の生成を避ける。GC対策)
- 時間依存の処理は `delta` を使う。フレーム数に依存させない
- 作ったもの(オブジェクト、タイマー、イベントリスナー)は、シーン終了時に `destroy` / `off` で**必ず解除**する
- 画面サイズ・`SCALE`・タイルサイズ・速度などは `src/config/` から参照する。**`960`、`16`、`320` などを直書きしない**
- ピクセルアート設定(nearest、`roundPixels` 等)は設定箇所で一括管理し、シーンごとに上書きしない
- 描画順は `depth = y`(DECISIONS.md)。独自の depth 値を散在させない
- 物理判定は先頭キャラのみ(パーティ追従の方針)。後続キャラに物理ボディを付けない

---

## 7. データ・テキスト・ID

- 会話・アイテム・敵・技・イベントは **JSON に置く**。コードに直書きしない
- 画面に出す文字列は**ID参照**。実文は `ja.json`(コード中に日本語の表示文を書かない)
- ID形式は `種類.分類.名前`(例: `item.key.rusty`)。フラグは `分類.名前`
- 新しい ID を使ったら、対応する定義(`ja.json` 等)も**同じ変更の中で追加**する
- フラグ番号を使う場合は「追加のみ。並べ替え・削除は禁止」
- セーブ形式を変えたら、**必ずマイグレーション関数を追加**する(DECISIONS.md の8章)

---

## 8. 依存(ライブラリ)の追加

**承認なしに `package.json` を変更しない。** 追加したい場合は、先に次を示す。

1. 追加する理由(標準機能や既存依存では足りない点)
2. 代替案(自作する、別ライブラリ、追加しない)
3. サイズ・保守状況・**ライセンス**
4. 推奨案

承認後は、バージョンを**完全固定**(`^` や `~` を付けない)で追加する。

---

## 9. エラー処理とログ

- **例外の握りつぶし禁止**(空の `catch`、`catch` して無視)
- 起こりうる失敗(セーブ読み込み失敗、ストレージ容量、コード形式不正)は、戻り値で表現するか、呼び出し側が扱える形のエラーを返す。ユーザーに伝える経路まで考える
- プログラムのバグ(ありえない状態)は、早い段階で明示的に例外にする
- セーブ関連は特に慎重に。書き込み失敗時に**既存データを壊さない**(別キーに書いて成功後に切り替え)
- `console.log` を残さない。開発用の表示は `?debug=1` の `DebugHud` を使う

---

## 10. セキュリティ・安全性

- ユーザー入力由来の文字列(プレイヤー名、バックアップコード、読み込んだJSON)を `innerHTML` に入れない。`textContent` を使う
- 外部から読み込んだデータを `eval` / `new Function` で実行しない
- API キー・トークン等の秘密情報をコードやリポジトリに置かない(本プロジェクトはサーバーなしだが、将来のため)
- 素材・フォントはライセンス確認後に追加し、`docs/ASSETS.md` に1行追記する

---

## 11. Git・ファイル操作

- AI は**勝手に `commit` / `push` しない**
- 破壊的な操作(`rm -rf`、`git reset --hard`、`git push --force`、`git clean`、ファイルの一括削除)は、実行前に確認を取る
- `node_modules/`、ビルド成果物、`package-lock.json` を手で編集しない
- コミットメッセージの提案形式: `種類: 変更内容`(種類 = `feat` / `fix` / `refactor` / `docs` / `chore`)。1コミット1目的

---

## 12. コメント・出力形式

- 識別子(変数・関数・クラス名)は**英語**、コメントは**日本語**
- コメントは「何をしているか」ではなく「**なぜそうしているか**」を書く(詳細は `READABLE_CODE.md`)
- チャット形式で依頼されたときは、ファイルごとに全文を出し、先頭に `// path: src/...` を付ける(AI_PROMPT.md の指示)
- **エディタ上でファイルを直接編集できる環境(エージェント機能)では**、全文の貼り付けではなく、対象ファイルを直接・最小差分で編集する。`// path:` 行をファイルに書き込まない

---

## 13. 完了時の報告テンプレート

作業の最後に、次の形式で簡潔に報告する。

```
## 変更内容
- (何をしたか。1〜3行)

## 変更ファイル
- src/...(新規 / 変更)

## 動作確認
- 実行したこと:(例: tsc --noEmit は通過 / 未実行)
- 確認手順:(何をして何が起きれば正しいか)
- 状態:検証済み / 未検証

## 気づいた点(修正はしていない)
- (あれば)

## 確認したい点
- (あれば)
```

## 14. 禁止事項チェックリスト

提出前に確認する。

- [ ] 依頼と無関係なコードを変更していない
- [ ] 確定事項(DECISIONS.md)に反していない
- [ ] `any` / `!` / `@ts-ignore` を使っていない
- [ ] マジックナンバーを `src/config/` 以外に書いていない
- [ ] 表示テキストを直書きしていない(ID参照 + `ja.json`)
- [ ] 承認なしに依存を追加していない
- [ ] 例外を握りつぶしていない / `console.log` を残していない
- [ ] 状態を二重に持っていない
- [ ] 未検証のものを「動く」と書いていない

## 付録A. 層と依存方向(草案)

> 実装が進んで実態と違ってきたら、**コードより先にここを更新する**。
> 設計の「確定」は `DECISIONS.md` が正。ここは配置の補足。

矢印は「依存してよい」方向。**逆向きは禁止**。

```
scenes/ ──▶ entities/, systems/, ui/ ──▶ core/ ──▶ config/
save/ ──▶ core/(GameStateの型のみ)
data/(JSON)は誰からでも読める(読み取り専用)
```

| 層 | 役割 | Phaser依存 |
|---|---|---|
| `config/` | 定数(解像度・SCALE・タイルサイズ・速度・入力時間) | なし |
| `core/` | `GameState`(純粋データ)、`EventBus`、`EventRunner` | **なし** |
| `save/` | セーブ、マイグレーション、バックアップコード、`IStorage` | **なし** |
| `systems/` | 入力・当たり判定・会話・マップ・追従・音声・多言語 | あり(一部なし) |
| `entities/` | プレイヤー、NPC、調べられる物、仲間 | あり |
| `ui/` | 会話ウィンドウ、メニュー、操作盤、DebugHud | あり |
| `scenes/` | Boot / Title / Field / Scenic / Battle / UI | あり |

- `scenes/` 同士は直接参照せず、`EventBus` か `GameState` 経由で連携する
- `systems/` 同士の依存は可だが循環させない。`entities/` は `scenes/` を import しない
- 状態の置き場所: 進行フラグ・所持品・パーティ・お金・現在地は `GameState`(セーブ対象)。カーソル位置・アニメなど一時的な表示状態は各シーン/UI(セーブしない)。入力状態は `InputSystem`(`InputSource` が書き込み、ゲームは読むだけ)
- シーン終了時は、作った物・リスナーを必ず解除する(6章)

---

## 付録B. 用語・命名の対応表

**同じ概念に複数の名前を使わない**ための辞書。新語が出たら1行追記してよい(既存行は変更しない)。

| 日本語 | コード上の名前 | 説明 |
|---|---|---|
| シンボルエンカウント | `SymbolEncounter` / `enemy` | 敵が見えていて、触れると戦闘開始 |
| 先頭 / 後続 | `leader` / `follower` | 物理判定は先頭のみ |
| パーティ追従 | `PartyFollowSystem` | 先頭の移動履歴を後続がなぞる |
| 調べる | `interact` | 向いている先を直接調べる(Aボタン) |
| アクション | `action` | 入力の抽象名(`confirm` など)。キー名ではない |
| 入力源 | `InputSource` | キーボード・操作盤・ゲームパッド |
| 操作盤 | `TouchPad` | スマホ縦持ちの画面下のHTMLボタン群 |
| ラッチ | `latch` | 押下を一定時間保持して取りこぼしを防ぐ |
| イベント / 命令 | `event` / `command` | 演出の命令列(JSON)/ その1ステップ |
| フラグ | `flag` | 進行状況の値。`分類.名前` |
| マイグレーション | `migration` | 古いセーブ形式を新形式へ変換する関数 |
| バックアップコード | `backupCode` | セーブを文字列化する任意機能 |

動詞の使い分け: `get`(すぐ返る)/ `find`(見つからないことがある → `T | undefined`)/ `create`・`spawn`(新規作成)/ `compute`(計算)/ `load`・`save`(外部との入出力、非同期)/ `is`・`has`・`can`(真偽値)

単位の接尾辞: `Ms` `Sec` `Px` `Tile` `Deg` `Rad`(例: `INPUT_LATCH_MS`)

ファイル名・ID形式は `DECISIONS.md` 10章に従う。
