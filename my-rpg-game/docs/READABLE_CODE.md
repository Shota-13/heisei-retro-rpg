# READABLE_CODE.md — 読みやすいコードの書き方

『リーダブルコード』(Dustin Boswell / Trevor Foucher 著、角 征典 訳、オライリー・ジャパン)の考え方を、
このプロジェクト(TypeScript + Phaser)向けに要約・再構成したもの。例はすべてこのプロジェクト用に作成した。
書籍の文章は転載していない。詳細は原著を参照。

## 根本原則

> **コードは、他の人(未来の自分とAIを含む)が最短時間で理解できるように書く。**

- 行数の少なさより、**理解にかかる時間**の短さを優先する
- 「動く」は最低条件。「読んで分かる」まで含めて完成
- 迷ったら、**初見の人が10秒で意図を言えるか**で判断する

---

## 1. 名前に情報を詰め込む

### 1-1. 具体的で、意味が伝わる単語を選ぶ

| ✕ 曖昧 | ◯ 具体的 |
|---|---|
| `getData()` | `loadMapJson()` / `readSaveSlot()` |
| `handle()` / `process()` / `do()` | `startDialogue()` / `applyDamage()` |
| `tmp` / `val` / `ret` | `nextPosition` / `damageAmount` / `foundNpc` |
| `list` / `arr` | `partyMembers` / `activeEvents` |

- `data` / `info` / `manager` / `util` / `helper` のような**何でも入る名前**は避ける
  (使うなら範囲を絞る。例: `SaveManager` は「セーブの読み書きを管理する」と言い切れるときだけ)
- ループ変数 `i` `j` は、狭いスコープ(数行)に限って許可。入れ子や長いループでは意味のある名前にする

### 1-2. 単位・属性を名前に含める

```ts
// ✕ 何の単位か分からない
const speed = 60;
const delay = 120;

// ◯ 単位が分かる
const MOVE_SPEED_PX_PER_SEC = 60;
const INPUT_LATCH_MS = 120;
```

- 時間は `Ms` / `Sec`、距離は `Px` / `Tile`、角度は `Deg` / `Rad` を付ける
- 他にも、検証前後(`rawText` と `escapedText`)など、**注意が必要な性質**は名前に出す

### 1-3. 名前の長さはスコープに比例させる

- 数行で終わる変数は短くてよい(`npc`)
- クラスのプロパティや公開関数は、単独で読まれても意味が通る長さにする(`currentDialogueLine`)
- 略語は、プロジェクト内で共通のもの(`HP`, `BGM`, `SE`, `NPC`)だけ。独自略語は作らない

### 1-4. 真偽値は「真のとき」が明確な名前にする

```ts
// ✕
let flag = false;
let status = true;
let notVisible = false;   // 否定形は二重否定を生む

// ◯
let isTalking = false;
let hasKey = true;
let canMove = true;
let isVisible = true;
```

- 接頭辞 `is` / `has` / `can` / `should` を使う
- **否定形の名前を避ける**(`isNotReady` → `isReady`)

### 1-5. 誤解されない名前にする

- 範囲を表すとき: 含む/含まないを明示する(`minX`/`maxX` は両端を含む、`start`/`endExclusive` など)
- 「境界」を決めたら、全体で同じ規則にする
- `get` / `find` / `create` / `compute` で**動詞を使い分ける**
  - `get`: すぐ返る(単純な取得)
  - `find`: 探す。見つからないことがある(戻り値は `T | undefined`)
  - `compute` / `calculate`: 計算コストがある
  - `create` / `spawn`: 新しく作る
- 命名の対応表は `CODING_RULES.md` の付録Bを参照

## 2. 見た目(整形)を整える

- インデント・改行・空行の規則を**ファイル全体で揃える**。既存ファイルのスタイルに合わせる
- 関連する処理を**空行でまとまり(段落)に分ける**。1つのまとまりは1つの話題
- 似た処理は**似た見た目**に並べ、違うところだけが目立つようにする
- 宣言や引数は、意味の順(関連するもの同士)に並べる。アルファベット順にしない理由があれば従う
- 長い行(目安120桁)は、意味の切れ目で改行する

```ts
// ◯ 似た処理は並べ、違いが分かるようにする
const upPressed    = input.isDown('up');
const downPressed  = input.isDown('down');
const leftPressed  = input.isDown('left');
const rightPressed = input.isDown('right');
```

## 3. コメントの書き方

### 3-1. 書かないコメント
- コードを読めば分かることの繰り返し
- 悪い名前を補うためのコメント(コメントを書く前に**名前を直す**)

```ts
// ✕ そのまま言い直しているだけ
// プレイヤーのHPを減らす
player.hp -= damage;

// ✕ 名前が悪いのでコメントで補っている
// 移動履歴の間隔(px)
const d = 4;
// ◯ 名前で解決
const HISTORY_RECORD_INTERVAL_PX = 4;
```

- 使わなくなったコードを**コメントアウトして残さない**(Gitに履歴がある)

### 3-2. 書くコメント
1. **なぜそうしたか**(意図、理由、トレードオフ)
2. **コードの欠点・注意**(`TODO` / `FIXME` / `NOTE`、直せない理由)
3. **定数の根拠**(なぜその値か)
4. **全体像**(ファイルやクラスの冒頭で、役割と他との関係を数行で)
5. **ハマりどころ**(読んだ人が間違えそうな点、Phaser特有の落とし穴)

```ts
// 押下を120ms保持する。タップが短すぎて1フレームの間に離されても、
// 次のフレームで必ず1回は処理するため。(DECISIONS.md 3章「入力の堅牢性」)
export const INPUT_LATCH_MS = 120;
```

### 3-3. コメントの質
- 短く、正確に。曖昧な代名詞(「これ」「それ」)を避ける
- 実例(入力→出力)を1つ添えると、長い説明より伝わることがある
- コードを変えたら、コメントも**同時に**直す。古いコメントは嘘より悪い

## 4. 制御フローを読みやすくする

### 4-1. 条件式の並び
- `if (a == b)` のように、**調べる対象(変化する値)を左、比較対象(定数)を右**に置く
- 否定の条件より**肯定の条件**を先に書く。簡単な/重要なケースを先に処理する

### 4-2. 早期 return(ガード節)でネストを浅くする

```ts
// ✕ ネストが深い
function interact(player: Player, target: Interactable | undefined): void {
  if (target) {
    if (target.isEnabled) {
      if (!dialogue.isOpen) {
        runEvent(target.eventId);
      }
    }
  }
}

// ◯ 異常系を先に抜けると、本筋が一直線で読める
function interact(player: Player, target: Interactable | undefined): void {
  if (!target) return;
  if (!target.isEnabled) return;
  if (dialogue.isOpen) return;

  runEvent(target.eventId);
}
```

- ネストは**3段以内**。越えたら、早期 return か関数抽出で浅くする
- ループの中は `continue` で早期に飛ばすと浅くなる

### 4-3. 三項演算子・複雑な分岐
- 三項演算子は**単純な場合のみ**。迷ったら `if / else`
- 三項演算子のネスト禁止
- `switch` は、網羅性チェック(`never` による)を付けて、命令やアクションの種類を漏れなく扱う

### 4-4. 関数の出口
- 関数の戻り値は、意味が分かる形で。`null` / `undefined` / `-1` を「失敗」の合図にするなら、型と名前でそれと分かるようにする

## 5. 巨大な式を分割する

### 5-1. 説明変数
複雑な式には、意味を持つ**名前付きの変数**を与える。

```ts
// ✕
if (Math.abs(player.x - npc.x) <= TILE_SIZE * 1.5 && Math.abs(player.y - npc.y) <= TILE_SIZE * 1.5) { ... }

// ◯
const talkRangePx = TILE_SIZE * 1.5;
const isNearX = Math.abs(player.x - npc.x) <= talkRangePx;
const isNearY = Math.abs(player.y - npc.y) <= talkRangePx;
if (isNearX && isNearY) { ... }
```

### 5-2. 要約変数・論理の整理
- 長い条件は、**結論に名前を付ける**(`const canStartBattle = ...`)
- ド・モルガンの法則で、否定を整理して読みやすくする
  - `!(a && b)` ⇔ `!a || !b` / `!(a || b)` ⇔ `!a && !b`
- 複雑なロジックは、**問題を言い換えて**簡単な形にできないか考える

## 6. 変数の扱い

- **変数を減らす**: 一度しか使わない一時変数や、結果をそのまま返すだけの変数は、名前が説明にならない限り不要
- **スコープを狭くする**: 変数は、使う直前に宣言し、使い終わったら見えなくなるようにする。クラスのフィールドにする前に、ローカルで済まないか考える
- **一度だけ書き込む変数を好む**: `const` / `readonly` を既定にする。値が変わる変数は、読み手の負担が増える
- **グローバル(モジュールレベル)の可変状態を作らない**
- 状態は1か所に置く(CODING_RULES.md 4章)

---

## 7. 無関係の下位問題を抽出する

- 関数を読んで「これは本題と関係ない」と感じる部分を、**独立した関数へ抜き出す**
- 抜き出した関数は、**プロジェクト固有の事情を知らない**形にすると、再利用・テストしやすい

```ts
// 例: 「角度から8方向を決める」は、画面やPhaserと無関係な純粋関数
export function angleToDirection(angleDeg: number): Direction8 { ... }
```

- 汎用的な処理(数学、文字列、配列)は `utils` に置く。ただし「何でも入る箱」にしない。種類ごとにファイルを分ける

---

## 8. 一度に1つのことをする

- 1つの関数/ブロックが**複数の仕事**をしていないか確認する
- 仕事を列挙して、**独立した仕事ごとに分ける**
  - 例: 「入力を読む」「状態を更新する」「描画に反映する」は別の段階
- 分けられない場合は、**段落(空行+コメント)で分けて**手順を明示する

```ts
update(deltaMs: number): void {
  // 1. 入力を読む
  const move = this.input.getMoveVector();

  // 2. 状態を更新する
  this.player.setVelocity(move, this.speedPxPerSec);

  // 3. 描画に反映する(depth = y)
  this.player.setDepth(this.player.y);
}
```

## 9. 思いをコードにする(説明できるコード)

- 処理を**日本語で簡単に説明**してみて、その言葉に近い名前・構造にコードを寄せる
- 説明が長くなる/うまく言えない部分は、設計が複雑すぎる合図
- 既存のライブラリや標準機能に**同じことをする関数がないか**先に探す

---

## 10. 短いコードを書く

- 最も読みやすいコードは、**書かないコード**
- 必要になるまで機能を作らない(YAGNI)。「将来使うかも」で作らない
- 要件を見直して、**簡単にできる方法**がないか考える
- 標準ライブラリ・Phaserの機能を**知る**。自作する前に調べる
- 使っていないコード(デッドコード)は削除する(ただしCODING_RULES.md 1章のとおり、依頼されたときのみ)

---

## 11. テストを読みやすくする

- テストは「**何を入れたら何が返るか**」が一目で分かるように書く
- テスト名は、**状況と期待結果**を書く(`境界の角度で方向が切り替わる`)
- 1つのテストで1つのことだけ確認する
- 大げさな準備が必要なら、本体の設計が複雑すぎる合図
- 入力と期待値は、できるだけ**具体的な値**で書く(ロジックを再実装して比較しない)

---

## 12. このプロジェクト固有の補足

| 項目 | ルール |
|---|---|
| 識別子 | 英語。ファイル・IDの命名規約は DECISIONS.md 10章 |
| コメント | 日本語。「なぜ」を書く |
| マジックナンバー | `src/config/` に定数化し、**単位付き**の名前にする |
| 画面の文字 | ID参照(`ja.json`)。コードに直書きしない |
| 型 | `any` 禁止。型名がドキュメントになるよう、意味のある名前を付ける |
| 変数名の略語 | `HP` `BGM` `SE` `NPC` など共通のもののみ |

## 13. セルフチェックリスト

書いたコードを見直すとき、次を確認する。

**名前**
- [ ] 名前だけで何をするか分かるか(`data` `tmp` `manager` のような曖昧語を使っていないか)
- [ ] 単位が必要な値に単位が付いているか
- [ ] 真偽値は `is/has/can` で、否定形になっていないか

**構造**
- [ ] 1つの関数が1つの仕事だけをしているか
- [ ] ネストは3段以内か(早期 return を使ったか)
- [ ] 複雑な式に説明変数を付けたか
- [ ] 変数のスコープは最小か。`const` で足りるか

**コメント**
- [ ] 「何を」ではなく「なぜ」を書いているか
- [ ] 古くなったコメント・コメントアウトしたコードが残っていないか

**全体**
- [ ] 不要な機能・先取りの抽象化を入れていないか
- [ ] 10秒で初見の人に意図を説明できるか
